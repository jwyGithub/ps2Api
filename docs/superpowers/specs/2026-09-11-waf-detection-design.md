# WAF 检测功能设计（403 分析 + 探针二分）

> 承接 `docs/403-waf-neutralization.md`（第 9 节 bin/cat 二分定位）。本文档设计把该手册的
> 人工排查流程固化为面板功能：离线分析自动定位嫌疑内容，在线探针自动收敛触发子串。
> 日期：2026-09-11。分两期交付，额度消耗不设限（用户明确）。

## 0. 背景与动机

2026-09-11 的 bin/cat 排查暴露三个手工瓶颈：

1. 签名扫描只能认已知特征（bin/cat 当天不在表里，日志误报"未检出"）；
2. 真正锁定触发源的是"与最近成功请求做逐叶 diff"（970 叶子 → 4 个差异 → 1 个新增
   4136B tool result），完全靠手工 Python；
3. 最终定位靠 repro403 探针七轮二分（改测试代码、手动跑 `go test`、换号）。

同时发现签名表已散落 4 处（waf.go 探测表、dashboard.js 预设、store.go 统计、文档），
加一个特征要改 4 个地方。

## 1. 签名表统一（前置重构）

- `internal/provider/waf.go` 的 `wafSignatureProbes` 成为唯一事实源；
- 新增 `GET /api/waf-signatures`：返回签名列表（含每条的类别说明），dashboard.js
  预设改为渲染时从该接口取；
- `store.go Cloudflare403SignatureSummary` 的 SQL `sig` 片段改为从 Go 列表程序化拼接
  （`LIKE '%<probe>%' OR ...`），不再手写字面量；
- 文档第 6 节 SQL 属人读手册，保持手写不动。

## 2. Phase A：403 离线分析

**页面**：新增 `page-waf.html`「WAF 检测」，左侧栏入口。

**列表区**：Cloudflare 403 记录列表（request_logs 过滤 `error_message LIKE '%Cloudflare%'`，
复用现有分页模式），行显示：时间、账号、出站体字节数、签名计数摘要。点行展开分析面板。

**分析面板三块**（全部本地计算，零出站请求、零额度）：

1. **签名扫描**：`WafSignatureHitCount` 逐特征计数（归一化逻辑复用 errors.go），显示
   "HTML 特征 ×N / bin/cat ×N / 零特征"；
2. **对照 diff（核心）**：
   - 对照组自动挑选顺序：同会话指纹最近成功 → 同账号最近成功 → 全局最近成功；
     下拉可手动换任意成功记录；
   - 对两个 `upstream_body`（JSON）解析后逐叶 diff（路径 + 叶子值），只展示
     新增/变更叶子；每片显示路径、字节数、内容预览（点击展开全文）；
   - 无可比对照时明确提示，允许手动指定。
3. **体积画像**：本条 bytes 与当天成功/失败分桶分布对照（分桶 SQL 复用手册第 7 节）。

**API**：`GET /api/waf/analyze?log_id=X&baseline_id=Y`（baseline_id 可选，缺省自动挑）。
响应：签名计数、diff 叶子数组、体积分桶、自动挑选的对照 id 及其选取原因。

## 3. Phase B：在线探针二分

**入口交互（半自动）**：分析面板中差异叶子带勾选框（默认全选），人工可先排除明显无关
叶子，点「发起探针」→ 确认弹窗（显示：变体预估数、账号、模型）→ 开始。

**探针算法**：

1. **叶子轮**：每个勾选叶子单独作为变体（基于对照组 body，只替换该叶子），经网关打进
   上游实测；2 次重复确认（403 实测为确定性拦截，2 次足够）；
   全部放行 → 提示触发可能是组合特征或对照组已含特征，建议换对照或转手工；
2. **行级二分轮**：对命中叶子按行二分拆片（每片用良性散文 padding 到等长，方法同
   repro403 的 `padTo`），~log2(N) 轮收敛到触发子串；每片同样 2 次重复。

**执行模型**：后台 job。

- `POST /api/waf/probe`：参数 log_id、baseline_id、选中叶子路径列表、账号 id（可选，
  缺省自动挑活跃号）、模型（默认 claude-haiku-4-5）。返回 job_id；
- `GET /api/waf/probe/{job_id}`：轮询进度——已完成变体、每变体结果（放行/403/其他、
  Ray ID）、当前收敛区间；完成后返回"触发子串"结论；
- 页面轮询展示（复用现有 dashboard 轮询模式），完成后展示结论与证据表。

**实现位置**：provider 层 `p.Chat` + 重置会话 + 唯一 nonce（与 repro403 相同路径），
**不走 router**：探针不占重试预算、不触发账号冷却、不写 request_logs 常规统计
（探针结果只存在于 job 报告里）。

**安全边界**：

- 「发起探针」按钮 + 确认弹窗 = 显式人工动作（等价 REPRO_403=1 的哲学）；
- 同一时刻仅允许一个探针 job（重复点击直接拒绝并提示）；
- 探针 job 不持久化，服务重启即丢（排查工具，非业务数据）。

## 4. 不做的事（YAGNI）

- 不做"一键把新特征加入中和规则"：规则改动涉及正则安全与模型可读性权衡，保持
  代码 + 单测门禁；
- 不做探针结果入库/告警：报告即看即止，特征确认后走正常代码流程；
- 不做全自动二分：无解场景（全放行）会白烧请求，半自动勾选即可。

## 5. 测试与验收

**单测**：

- 逐叶 diff：相同 body、不同叶子、叶子增删、JSON 解析失败兜底；
- 签名统一：API 返回与 wafSignatureProbes 一致、store.go 拼接 SQL 与预期一致；
- 探针拆片：padding 等长、二分收敛、全放行分支；
- 对照组挑选：三级回退顺序、无对照兜底。

**端到端验收（用今天的真实案例）**：

- 以 2026-09-11 b577d7cb 的 403 记录为样本：A 期 diff 应锁定 README 叶子
  （toolResponses[0].content.message 93B→4136B）；
- B 期对叶子轮 + 行级二分应收敛到 `./bin/catpaw2api -config config.json` 一行；
- 探针结论页能直接给出 bin/cat 特征证据。
