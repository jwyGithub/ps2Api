# ps2api 新前端开发规划（Spec + Plan）

> 目标：用 `page/`（TanStack Start + tRPC + better-auth）重建管理面板，替换 `internal/dashboard/` 的静态实现，并落地 7 个功能域。
> 关键决策（已确认）：**① BFF 模式　② API Key 硬性限流　③ 账号卡片/列表双视图可切换　④ 目标：多用户 + 后续水平扩展　⑤ DB 现在上 MySQL、Redis 接口预留　⑥ 网关留在 Go 做架构重构（不迁 Rust）**。

---

## 零、方向性决策（最新，2026-08-20）

> 目标从「单进程部署」调整为「**多用户使用 + 后续基于当前功能水平扩展**」。这改变了此前基于「单进程」前提得出的 DB 结论，特此更新。先实现基础功能，架构上为多实例留门、但不提前部署重组件。

### 决策 D1 · 数据库现在就上 MySQL
- **前提变化**：不再锁定单进程；明确要多用户、未来扩展。SQLite 在多实例下是硬伤（文件锁 + 无法共享）。
- **决策**：借这次重构把 store 层直接写在 **MySQL** 上，一步到位，避免将来「SQLite→MySQL」的痛苦迁移（并发写锁、方言差异、数据搬迁）。
- **落地约束**：store 层保持在 `database/sql` 接口之上，业务层不感知具体驱动/方言，便于后续演进。

### 决策 D2 · Redis 暂缓，用接口预留
- **理由**：Redis 的刚需触发点是「多实例共享状态」（限流计数、会话）。当前是「先实现基础功能」，单实例即可跑。
- **决策**：把 **限流 / 缓存 / 会话** 抽象成接口（如 `RateLimiter` / `Cache`），默认**进程内内存实现**；等真正上多实例那天，加一个 **Redis 实现 + 改配置**即可，今天零额外运维负担。

### 决策 D3 · 网关留在 Go 做架构重构，不迁 Rust
- **判断**：现有网关「混乱、扩展能力差」是**架构设计问题，不是语言问题**——换 Rust 不会自动变清晰，反而把架构问题当语言问题解是重写项目的常见坑。
- **性能**：API 代理是 **I/O 密集**（瓶颈在上游 LLM 延迟），Go 足够；Rust 的优势在 CPU 密集场景，这里用不上。
- **风险**：同时做「前端重构」和「网关重写语言」= 一次背两个高风险，任一出问题都会拖垮整体。
- **决策**：网关**留在 Go**，做一次**架构重构**——清晰的中间件/插件链、稳定的 provider 抽象接口、配置驱动，真正解决「难扩展」。仅当出现**实测且具体**的理由（CPU 瓶颈、内存、需要 WASM 插件生态等）时，再单独立项考虑 Rust，且不与前端重构搅在一起。

### 对既有章节的影响
- **鉴权/多用户**：需要引入用户「角色」（如 admin/viewer），并在数据层增加 `role` 列（详见第六节开放问题2）。
- **限流方案（功能4 / P5）**：由「进程内硬限流」改为「**进程内计数器实现 + `RateLimiter` 接口预留 Redis**」，语义不变（超额 429/402 拒绝），仅实现可替换。

## 一、整体架构（BFF 模式）

```
浏览器 (React SPA)
   │  只认 tRPC / better-auth，浏览器永远看不到 Go 的管理凭据
   ▼
TanStack Start 服务端 (Node/Nitro)  ← BFF 层
   ├─ better-auth：登录/注册 + 会话(Cookie)，用户库(MySQL，见决策 D1)
   ├─ tRPC procedures：受会话保护，转发到 Go /api/*
   └─ 持有 ADMIN_TOKEN（服务端环境变量，注入到转发 Go 的请求头）
   │  HTTP + ADMIN_TOKEN
   ▼
Go 网关 (internal/api)
   ├─ /v1/*   推理端点：用 client API Key 鉴权（功能4，硬限流）
   ├─ /api/*  管理端点：用 ADMIN_TOKEN 鉴权（仅 BFF 可调）
   └─ MySQL：账号/日志/统计/设置/告警/【新增】api_keys/proxies/role（见决策 D1）
```

### 鉴权边界拆分（重要改动）
当前 Go 的 `auth()` 用**同一个** `api_key` 同时守护 `/v1/*` 与 `/api/*`。BFF 模式下拆成两套：

| 端点 | 谁来调 | 凭据 | 说明 |
|------|--------|------|------|
| `/v1/*` 推理 | 外部客户端（Claude/OpenAI SDK） | **client API Key**（功能4，多把、带额度） | 校验 `api_keys` 表 + 硬限流 |
| `/api/*` 管理 | 仅 BFF（服务端转发） | **ADMIN_TOKEN**（单个，环境变量/设置） | 浏览器永不持有；用户能否触达取决于 better-auth 会话 |

> 兼容：保留旧的单 `api_key` 设置作为 client key 的兜底，迁移期不破坏现有客户端。

## 二、按功能域的实现方案与后端改动评估

图例：改动量 **S**=小(<0.5d) / **M**=中(0.5–1.5d) / **L**=大(>1.5d)。「后端」指 Go 侧。

### 功能1 · 登录 / 注册（注册可由系统配置开关）
- **现状**：Go 无任何用户/会话概念；scaffold 的 better-auth 已装但**未配置数据库**，当前无法真正登录。
- **前端**：better-auth 邮箱+密码；新增 `/login`、`/register` 路由与守卫；未登录重定向到登录页。
- **注册开关**：Go 设置新增 `registration_enabled`（功能6）。注册前经 tRPC 读取该开关；服务端 sign-up 也二次校验，禁用时直接拒绝（不仅隐藏 UI）。
- **首次引导**：首个注册用户设为管理员，之后可在系统设置里关闭注册。
- **后端改动**：仅在 `settingDefs` 加 `registration_enabled`（**S**）。用户库全在 BFF 的 better-auth（**M**，含配 SQLite 适配器）。

### 功能2 · 账号管理（卡片 + 列表双视图）
- **现状**：`/api/accounts` GET、POST（手动加 token）、`/export`、`/import`、`DELETE`、`PATCH`(启停) **均已存在**；`Account` 结构体已含全部所需字段：`plan`(类型)、`createdAt`、`quotaLimit`(总额度)、`quotaUsed`、`quotaRemaining`、`lastUsedAt`、`email`、`quotaCycleEnd`(重置日期)。
- **前端**：卡片网格 + TanStack Table 列表，顶部切换按钮（视图偏好存 localStorage）；新增/导入/导出/删除/启停对接现有接口。
- **后端改动**：基本无。可选补一个「编辑账号」`PATCH`（当前仅启停），非必需（**S，可选**）。

### 功能3 · 统计分析（今天/24h/7d/30d/自定义范围 + 消耗额度 + 剩余总额 + 预测）
- **现状**：`/api/analytics` + 额度预测**已实现**；`/api/stats` 提供汇总。
- **待核实/扩展**：`analytics` 是否支持自定义 `from/to` 时间范围（需读 `internal/store/analytics.go`）。若只支持固定档，需加 range 参数（**M**）。
- **剩余总额**：由所有启用账号 `quotaRemaining` 汇总（可前端聚合或加一个汇总字段）。
- **前端**：区间选择器 + 图表（需引入图表库，见技术选型）。
- **后端改动**：range 参数扩展（**S–M**）。

### 功能4 · API Key 管理（多把 key，硬性限流）
- **现状**：仅**单个** `api_key` 设置，`/v1/*` 与 `/api/*` 共用。**需要新建体系**。
- **后端改动（L，本规划最重）**：
  1. 新表 `api_keys`：`id, name, key_prefix, key_hash, quota_limit(NULL=不限), quota_used, enabled, created_at, last_used_at`。
  2. Store 方法：`CreateAPIKey / ListAPIKeys / DeleteAPIKey / SetAPIKeyQuota / GetAPIKeyByRaw / IncrAPIKeyUsage`。
  3. 重写 `/v1/*` 的鉴权：按哈希匹配 `api_keys`；命中后**请求前**校验额度，超额返回 `429`（或 `402`）拒绝；请求后按 `total_tokens` 累加 `quota_used`。限流通过 `RateLimiter` 接口实现，默认**进程内计数器**，预留 Redis 实现（见决策 D2）。
  4. 新增管理接口 `/api/keys`（GET/POST/DELETE/PATCH）。
  5. 迁移 + 旧单 key 兜底。
- **前端**：Key 列表、创建（**原文仅创建时展示一次**，库里存哈希）、复制、删除、设置额度（数字或「不限」）。

### 功能5 · 模型管理（启用部分模型 + 单模型测试）
- **现状**：`PostmanModels` 为硬编码列表，`/v1/models` 全量返回，无启停/测试。
- **后端改动（M）**：
  1. 持久化启用集合：设置项 `enabled_models`(JSON 数组) 或新表；`/v1/models` 只返回启用项，推理时拒绝已禁用模型。
  2. `/api/models` GET（全部 + `enabled` 标记）、PATCH（启停）。
  3. `/api/models/{id}/test`：发一条最小请求走 router，返回 `ok/latency/error`。
- **前端**：模型列表 + 开关 + 「测试」按钮（显示延迟/结果）。

### 功能6 · 系统设置
- **现状**：白名单 `settingDefs` + 通用 `getSettings/putSettings` **已就绪**，前端可按 `defs` 动态渲染表单。
- **后端改动（S）**：向 `settingDefs` 增补：`registration_enabled`（功能1）、以及后续需要的键（如默认额度等）。
- **前端**：按 `defs` 动态生成表单（number/bool/text），保存走 PUT。

### 功能7 · 代理管理（多代理、单独启停、单独测试、后端代理池）
- **现状**：**代理池已实现**——`proxy_urls`(多行文本) + `proxy_enabled`(开关) + 账号粘性/403 轮换 + `/api/proxy-check`。但代理是**一整块文本**，无法单独启停/命名。
- **后端改动（M）**：
  1. 新表 `proxies`：`id, url, label, enabled, last_ok, latency_ms, created_at`。
  2. Provider 的代理列表来源从 `proxy_urls` 设置改为**读取启用的 proxies 行**（池逻辑基本复用）；保留 `proxy_enabled` 全局开关。
  3. `/api/proxies` GET/POST/DELETE/PATCH；`/api/proxies/{id}/test`（复用 `CheckProxies` 单条）。
  4. 迁移：把旧 `proxy_urls` 文本拆分导入新表。
- **前端**：代理列表、新增、启停、单条测试（延迟/连通性）。

## 三、技术选型确认（page/ 已具备 vs 需补）
- **已具备**：TanStack Start/Router/Query/Store/Table、tRPC v11、better-auth、Tailwind v4、shadcn/ui、zod、lucide、superjson。
- **需补**：
  - better-auth 的**数据库适配器**：按决策 D1 统一用 **MySQL**（Kysely + mysql2 方言），与 Go 侧同一 DB 实例、不同库/表前缀，避免再引入 SQLite。
  - **图表库**（功能3）：建议 `recharts` 或 `@tanstack` 生态无图表 → 用 `recharts`（轻、React 友好）。
  - shadcn 组件按需生成（table/card/dialog/form/switch/tabs/toast 等）。
  - 环境变量：`GO_API_BASE`(Go 地址)、`ADMIN_TOKEN`、better-auth secret；开发期跨端口用 Vite proxy 或直接服务端 fetch。

## 四、前端路由与页面规划
```
/login, /register                 功能1（无布局）
/(app)                            受保护布局：侧栏 + 顶栏 + Toast
  /                     概览(汇总KPI，复用stats)
  /accounts            功能2（卡片/列表切换）
  /analytics           功能3（区间 + 图表 + 预测）
  /keys                功能4（Key 管理）
  /models              功能5（模型启停/测试）
  /proxies             功能7（代理管理）
  /settings            功能6（动态设置表单，含注册开关）
```
tRPC 路由分组：`auth / accounts / analytics / keys / models / proxies / settings`，每个 procedure 用受会话保护的 `protectedProcedure`，内部用带 `ADMIN_TOKEN` 的 Go 客户端转发。

## 五、分阶段实施计划（建议顺序）

| 阶段 | 内容 | 功能 | 后端改动 | 估算 |
|------|------|------|----------|------|

| **P3 系统设置** | 按 defs 动态表单 | 6 | 增补 defs(S) | S |
| **P4 统计分析** | 区间选择 + 图表 + 预测 + 剩余总额 | 3 | range 扩展(S–M) | M |

## 六、风险与开放问题
1. **额度口径**：功能4 的「额度」按 **token 总量** 还是**请求次数**计？（建议 token，和账号额度口径一致）
2. **管理员/多用户**：目标已确定为多用户 → 需引入角色（admin/viewer）并加 `role` 列。首个用户即管理员是否够用，还是需要后续可管理角色的界面？
3. **模型测试计费**：单模型测试会真实消耗账号额度，是否需限频/标记？
4. **代理迁移**：旧 `proxy_urls` 文本是否需要一键迁移到新表并保留兼容期？
5. **部署形态**：目标已转向多用户/可水平扩展（不锁死单进程）。Go 与 TanStack 建议两进程独立部署，便于各自扩展；DB 用 MySQL、状态类组件走接口预留 Redis（见决策 D1/D2）。仍需确认：是否需要多实例负载均衡的时间点。
