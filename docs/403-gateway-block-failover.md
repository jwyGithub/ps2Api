# 生产环境 403（Cloudflare）挂起问题：分析与修复

> 本文档记录一次生产事故的根因分析与修复方案，并以**语言无关**的方式描述设计，方便后续迁移到其他语言（Node/Python/Rust 等）时作为参考。
> 涉及服务：Postman → API 的 HTTP 代理/网关（Go 实现）。

---

## 1. 现象（Symptom）

- 生产服务在命中 `Postman gateway rejected request (403, Cloudflare)` 后**永久挂起**。
- 客户端（终端 / 模型）拿不到任何响应，也拿不到明确的失败信号，会话卡死。
- 重试无效：同一请求反复失败。

---

## 2. 根因分析（Root Cause）

基于 491 条 trace 实证数据得出两条独立根因：

### 2.1 403 的真正原因 = 账号身份被 Cloudflare 风控

- 全部 **69 次 403 只集中在 4 个账号上**（acct 14 / 16 / 19 / 21），拦截率 35%–86%；其余所有账号 **0 拦截**。
- **同样 117595 字节**的请求体：在健康账号上成功，在被烧账号上必被拦截。
- 结论：**403 与请求体大小无关、与出口 IP 无关**，而是 Cloudflare 按**账号指纹 / 账号状态**判定（与其官方 Bot Management 行为一致）。
- 观测到的 Cf-Ray 边缘节点均为 `-LAX`，进一步佐证是账号维度而非网络维度的问题。

> 早期假设「超大 payload 是触发 403 的常见诱因」被数据推翻，应降级为「可能的加重因素之一」。

### 2.2 为什么会永久挂起

两个缺陷叠加：

1. **重试策略错误**：旧逻辑遇 403 只对**同一粘性账号**重试 3 次（0 次换号）。被烧账号无论重试多少次都必然 403。
2. **流式协议未干净收尾**：流式在联系上游**之前**就先发了 `message_start`；失败后只发 `event: error` 就 `return`，**缺少 `message_stop`**。客户端等不到流终止事件 → 永久挂起。

---

## 3. 修复方案（Fix）

### 3.1 遇网关拦截时 failover 到健康账号

- 错误分类：区分 `GatewayBlocked`（Cloudflare/网关拦截，可换号重试）与 `RequestRejected`（请求本身非法，换号无意义）。
- `Chat` 与 `Stream` 路径遇 `GatewayBlocked` 时：
  1. **排除当前账号** + 给它打**冷却标记**；
  2. 退避（backoff）后 **failover 到下一个健康账号**；
  3. 账号**全部耗尽**时，返回**明确的网关拦截错误**（带 `GatewayBlocked` 标记），而不是笼统的 "no accounts"。

### 3.2 账号池冷却（自动降级 + 自动恢复）

- 账号池新增**网关冷却表**与 `MarkGatewayBlocked(accountID)`。
- 选号 `Next()` 在冷却期内**优先跳过**被烧账号；若全部处于冷却，则兜底仍可返回（避免完全无号可用）。
- 冷却到期后账号**自动恢复**参与调度 → 被烧号自动降级、自愈。

### 3.3 流式统一「延迟开流 + 干净收尾」

三个流式处理器（Anthropic / OpenAI Chat / Responses）统一改为：

- **延迟开流（deferred start）**：等**首个真实增量**到达后，才提交 HTTP `200` 与首个流事件。
- **产出前失败**：回退为**干净的 HTTP 503 JSON 错误**（此时还没发任何流事件，可以直接返回标准错误体）。
- **已开流后失败**：补发协议对应的终止事件干净收尾：
  - Anthropic：`message_stop`
  - OpenAI Responses：`response.failed`
  - OpenAI Chat（SSE）：`[DONE]`
- 效果：终端能明确「任务结束」，模型知晓「本次未产生任何输出、可安全重做」，不再挂起。

### 3.4 可配置项

- 新增配置：**网关拦截冷却(秒)**，默认 `300`。

---

## 4. 迁移到其他语言时的要点（Checklist）

移植时请保留以下**行为契约**，而非具体 Go 实现：

1. **错误分类可区分**：至少区分「可换号重试的网关拦截」与「请求本身非法」两类，避免对非法请求做无意义换号。
2. **换号重试而非原号重试**：网关拦截必须触发跨账号 failover，并排除当前账号。
3. **账号级冷却，带 TTL 自动恢复**：被烧账号进冷却池，优先跳过；全冷却时兜底可用；到期自愈。冷却时长可配置（默认 300s）。
4. **流式必须延迟开流**：在拿到首个真实增量前，不要提交 200 / 不要发首事件。这样失败可回退为标准 HTTP 错误。
5. **流式失败必须干净收尾**：已开流后失败，务必补发协议规定的终止事件（`message_stop` / `response.failed` / `[DONE]`），否则客户端会挂起。
6. **账号耗尽返回明确错误**：failover 用尽账号时，返回带明确语义的网关拦截错误，而非「无可用账号」。

---

## 5. 已知取舍与后续建议（Trade-offs）

- **换号会丢失 Postman 服务端会话缓存**，但完整消息历史每次都会重放，正确性不受影响（仅损失缓存命中带来的性能收益）。
- **Cloudflare 侧无权限调整**；出口 IP 轮换保留为**次要手段**，不是主因解法。
- **被烧账号（14 / 16 / 19 / 21）**建议后续在面板上**停用或重新登录**，以刷新其 Postman 身份。
